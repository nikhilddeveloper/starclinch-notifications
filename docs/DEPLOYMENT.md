# Deployment guide

The assessment explicitly requires Django on Render and the frontend on Vercel. These files prepare deployment; they do not create accounts, incur charges or claim working hosted URLs.

## 1. GitHub

Create an empty repository in your own account. From the project root run git init, git add ., git commit -m "Build notification system", set your repository remote, then push the main branch. Review git status and staged files first. The .gitignore excludes local .env files, databases, credentials, dependencies and build output. Do not upload the employer's assessment document or email as repository assets.

Use a public repository only if you are comfortable sharing your implementation. Otherwise give the reviewer private access.

## 2. Render backend

Create a persistent PostgreSQL database, then import render.yaml as a Render Blueprint. The web service blueprint requests the free plan; database availability, expiry and current costs must be checked in your account before provisioning. You may provide a compatible external PostgreSQL URL. Do not deploy SQLite onto Render's ephemeral filesystem.

Set DATABASE_URL to the PostgreSQL URL, FRONTEND_URL to your exact Vercel origin, and choose strong ADMIN_USERNAME, ADMIN_EMAIL and ADMIN_PASSWORD values for the first deployment. SECRET_KEY is generated by the blueprint. Set provider variables and allowlists as described in the README when you are ready for real sandbox tests.

The build installs locked dependencies and collects static files. Startup applies migrations, adds missing Login/Logout templates and creates an admin only if it does not already exist. It never resets a pre-existing admin password. Remove ADMIN_PASSWORD after the first successful creation. Alternatively create an admin with python manage.py createsuperuser from an appropriately configured environment with database access.

The health check is /api/health/. Verify it returns {"status":"ok"}. Render's hostname is automatically added to ALLOWED_HOSTS. DEBUG=false forces HTTPS and requires PostgreSQL and a non-development secret. Keep NOTIFICATIONS_DRY_RUN=true until provider setup is finished. A sleeping free web service may take time to start; warm it before recording.

If deploying manually, use root directory backend, build command bash build.sh, start command bash start.sh, and the same environment variables.

## 3. Vercel frontend

Import the repository into Vercel and choose root directory frontend, framework Vite, build command npm run build, output directory dist and Node.js 22. Set VITE_API_URL=https://YOUR-RENDER-SERVICE.onrender.com/api. No server secrets belong in VITE variables. Deploy.

Set the final Vercel origin in the backend FRONTEND_URL and in the OneSignal website app settings. Redeploy/restart the backend after environment changes. Verify the frontend service worker exists at /OneSignalSDKWorker.js and serves JavaScript, not the index page. A Vercel preview URL is a different origin; keep the stable production origin for the recorded demo.

## 4. Acceptance checks

1. Health endpoint works over HTTPS; frontend signs in using the created admin.
2. Database data persists after a backend restart/redeploy.
3. Templates create/edit/toggle correctly. A non-staff account cannot manage templates.
4. Profile uses your own allowlisted phone/email; both consent choices are on.
5. Browser is subscribed; its UUID is allowlisted on the backend.
6. Both WhatsApp templates are actually APPROVED after Sync.
7. Turn NOTIFICATIONS_DRY_RUN=false. Test all three channels for Login and Logout. Confirm receipt, not just API acceptance.
8. Log out and log in again to fire both real triggers. Edit one message and retest; turn a channel off, fire its trigger, inspect skipped, turn on again.
9. Record the narrated walkthrough and verify reviewer access to the links.

Do not submit simulated logs as evidence of real delivery. PostgreSQL CI is included but has to run after the repository is pushed; it is not assumed to have passed locally.

## Optional worker

Inline mode avoids an extra hosting service for this assessment. For asynchronous processing, set NOTIFICATIONS_INLINE=false and separately run python manage.py process_notifications against the same database and provider environment. Check hosting costs before creating that worker. Never disable inline dispatch without starting a worker, or events will remain queued.
